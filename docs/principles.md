# 黒猫亭の開発方針

何を良しとするかを、1枚にまとめる。開発・レビュー・UI/UX・調査・PM の bot と人が、これを読めば同じ判断ができることをねらう。

- ここに書くのは、これまでに Issue・PR・`docs/spec.md`・`docs/setting.md`・`CLAUDE.md` で示された方針だけである。新しい方針はここで作らない。
- 括弧の中の番号は、根拠になった Issue か PR である。
- 作業の手順（テストや measure の回し方）は `CLAUDE.md` と README に書く。ゲームの決まりは `docs/spec.md` に、世界の設定は `docs/setting.md` に書く。

## 1. 遊ぶ人の体験を先に

- 不具合と、遊べなくなる問題を最優先にする（#185）。
- 店主の判断が結果につながった、という手応えを見せる。無力感だけを残さない（#130）。
- 死は「運が悪かった」ではなく、「一行が無茶をした」と読めるようにする（#91）。
- 遊んでみた感じから出た困りごとを、そのまま Issue にする（#105・#106）。

## 2. 参考作品は表面をまねない

- 参考作品は、見た目をまねない。その作品がなぜそう感じさせるのかという体験の芯を、黒猫亭の言葉で生かす（#152）。
- 仕組みの見た目（ろうそく、ゲストブックなど）は持ち込まない（#162・#163）。
- 店主が冒険者を動かさない、という黒猫亭の作りに合わないものは取り込まない（#151）。

## 3. 灰と死の重さを緊張感の芯として残す

- 蘇生は金で買えるが、失敗すれば灰になり、灰の次には何も残らない（setting.md「世界の手触り」）。灰と死の重さは緊張感の芯なので、取り返しのつかなさを薄める変更は絞る（#177）。
- 賭けの場面は残す。灰になる危険を承知で、もう一度だけ賭けられる（#183）。
- ロストする道を消さない。巡回隊が届く深さには上限がある（#165）。
- 死は淡々と一行で書く。倒れた者に二つ名の知らせは出さない（setting.md、#74）。ただし、ロストのときには何かひとこと残す（#163・#165）。
- 救いは小さく、個人的なものにする（setting.md）。去った者から届くのは小さな品までで、お金や紹介状は送らない（#74）。

## 4. 店主は冒険者を直接動かせない

- 店主は機会を差し出すだけで、決めるのは本人である。店主の判断は、支援・方針・誰に回すかを通して効く（#37）。
- 読むのは店主である。見込みや話の回し方で、強さや果たせる確率に補正を付けない（#37・#39）。
- 向き不向きは数字や条件で出さず、文面ににじませる（#37）。
- 店主の代わりに勝手に回す仕組み（番頭など）は作らない（#37）。
- 一行の考えは、危ないときだけ水晶に一行出す（#79）。

## 5. 伏せる情報と見せる情報

- 水晶で見ていなかった全滅は、遺体が街に着くまで、死因・階・倒れたことを出さない。生きていて帰りが遅い一行と、見た目で見分けられないようにする（#165・#172）。
- 依頼の額のような間接の手がかりからも漏らさない（#172・#174）。
- 水晶で最期を見ていたときは、その場で死亡とする（#165）。
- 「店主はそのとき水晶を見ていなかった」のような文は書かない（#165）。

## 6. 釣り合いは measure で、支援なしと支援ありの両方で確かめる

- 戦闘・成長・経済・ダンジョン・一行の動きなど、釣り合いに効く変更は、支援なしと支援ありの両方で測り、PR に書く（CLAUDE.md、#87・#119・#120・#122）。16種で揺れと区別がつかなければ、48種で測り直す（#120）。
- 表示だけの直しでは、シミュレーションの結果を変えない（#143）。釣り合いに効かない変更では measure は要らない（#152・#197・#199）。
- これまでに示された目安：
  - 支援ありで、迷宮を8〜10勝（五分か少し上）（#46）。
  - いちばん多い死因は4割ほどまで。ただし「この階にはこの怖い魔物」という個性は残す（#82）。
  - 店主への見返りは、釣り合いに響かせない程度にする（#72）。

## 7. 古い記録を壊さない。仕様は spec.md に書く

- 古い記録を読み込んでも壊れないこと。今あるセーブとの互換は必ず守る（#191・#194・#195）。
- 記録が足りない古いデータでは、出せる行だけを出す。空のかぎかっこや代わりの文は出さない（#152・#163）。
- 記録の形を変えたら、セーブの版を上げて移行を足す。表示だけの変更では上げない（#129・#163）。
- 振る舞いを変えたら、同じ変更で `docs/spec.md` を直す。書くのは遊ぶ人に見える振る舞いと決まりで、実装の細部は書かない。同じことは1か所にだけ書く（CLAUDE.md、#11）。
- 方針から決める直しは、先に spec.md に書いてから直す（#125）。

## 8. 書き方の手触り

- 説明しすぎない。笑いは乾いた冗談として出す（setting.md、#70・#72）。
- 評価の言葉（「早すぎた」「運が悪かった」）と、店主の心情は書かない。飾らず、事実だけを並べる（#152・#162・#163）。
- 「」に入れるのは本人の言葉だけである（#147）。
- 名前は一生使い回さない（#71）。
- 人名・店名・地名・「○日目」などは一続きにし、語の途中で折らない。閉じかっこだけが次の行に残らないようにする（#86・#88・#99・#163）。
- 水晶の一言は、水晶のログと同じ文体（ひらがな・分かち書き）にする（#79・#142）。
- 遊びに使う数字は算用数字で書く。地の文の言い回し（「五割増し」など）は漢数字のままでよい（#100）。金額は3桁で区切る（#143）。

## 9. 画面

- 375px と 1280px の両方で確かめる（#130・#163・#165・#172）。
- 押す所は44px以上にする（#85・#95・#197）。
- 赤は、全滅が近いなど本当に危ないときだけに使う。同じ状態の色は、水晶と札でそろえる（#79・#125）。
- 押し間違えると取り返しのつかないボタンに気をつける（#85）。

## 10. 実装の約束

- 文を組むときに乱数を引かない。すでにある状態から決まった順で選び、同じ記録からは同じ文になるようにする（#130・#162・#163）。
- 決まり方は、乱数の種で再現できるようにする（#165）。

## 11. 決め方

- 世界観（`docs/setting.md`）、大きな方針、仕様の分かれ道は azu さんに聞く（#70・#74・#79・#82）。
- それ以外の細かい点と順番づけは、下調べの案を基本に開発と PM で決め、決めたことを PR 本文に書く（#70・#74）。マージを保留するか、しきい値をどうするかは PM が決める（#120・#193）。
- 新しく決める必要のある点は、PR 本文に2〜3個の選択肢をつけて並べ、PM が azu さんに確かめてから反映する（#184・#185）。
- 1つの Issue に PR を1つ。ほかの Issue の直しは混ぜず、Issue の範囲より広げない（#143・#183）。マージは頼んだ側がする（#147）。
